## Reporting a Vulnerability

We take security vulnerabilities seriously. If you discover a security issue, please report it responsibly.

### How to Report

1. **Do NOT** open a public GitHub issue for security vulnerabilities
2. **Use GitHub's Private Vulnerability Reporting:**
   - Go to the repository's **Security** tab
   - Click **"Report a vulnerability"**
   - Fill out the private security advisory form
3. Include the following information:
   - Description of the vulnerability
   - Steps to reproduce
   - Potential impact
   - Any suggested fixes (optional)

### What to Expect

| Timeline | Action |
|----------|--------|
| 24 hours | Acknowledgment of your report |
| 72 hours | Initial assessment and severity classification |
| 7 days | Detailed response with remediation plan |
| 30-90 days | Fix deployed (depending on severity) |

### Severity Classification

| Severity | Response Time | Examples |
|----------|---------------|----------|
| **Critical** | 24-48 hours | SQL injection, auth bypass, data exposure |
| **High** | 7 days | XSS, CSRF bypass, privilege escalation |
| **Medium** | 30 days | Information disclosure, rate limit bypass |
| **Low** | 90 days | Minor issues, hardening improvements |

## Security Features

QueryfyAI implements multiple layers of security:

### Authentication & Session Security
- **HMAC-signed sessions** - Cryptographically verified session integrity
- **CSRF protection** - Token-based protection for state-changing operations
- **Session timeout** - Automatic expiration of inactive sessions
- **Secure token generation** - Cryptographically secure random tokens

### Input Validation & Sanitization
- **SQL injection prevention** - 26+ prompt injection patterns detected and blocked
- **Input sanitization** - All user inputs sanitized before processing
- **Query validation** - Generated SQL validated before execution
- **Read-only enforcement** - Only SELECT queries permitted by default

### SQL Security
- **SQL integrity verification** - Hash-based verification that SQL was generated by the system
- **Execution audit trail** - All SQL executions logged with session context
- **Result size limiting** - Prevents memory exhaustion from large result sets
- **Query timeout** - Prevents long-running queries from blocking resources

### Rate Limiting
- **Per-session rate limits** - Prevents abuse of generation endpoints
- **Per-action limits** - Different limits for generate, execute, export operations
- **Configurable thresholds** - Adjustable limits based on deployment needs

### Audit & Logging
- **Security event logging** - All security-relevant events logged
- **Sanitized error messages** - No sensitive data exposed in error responses
- **Audit trail** - Complete history of queries and executions per session

### Network Security (Production Deployment)
- **HTTPS enforcement** - TLS required for all connections
- **CORS configuration** - Restrictive cross-origin policies
- **Security headers** - Standard security headers (CSP, X-Frame-Options, etc.)

## Security Best Practices for Deployment

### Environment Variables
```bash
# Required for production
SECRET_KEY=<strong-random-key>           # Min 32 characters
CSRF_SECRET=<strong-random-key>          # Min 32 characters
ALLOWED_ORIGINS=https://yourdomain.com   # Restrict CORS

# Database connections
DATABASE_URL=<connection-string>         # Use SSL connections
```

### Docker Deployment
```yaml
# Use non-root user
user: "1000:1000"

# Read-only filesystem where possible
read_only: true

# Drop capabilities
cap_drop:
  - ALL
```

### Kubernetes Deployment
```yaml
# Pod security context
securityContext:
  runAsNonRoot: true
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
```

## Known Limitations

1. **No built-in user authentication** - Currently relies on session-based security. JWT authentication planned for future release.
2. **No RBAC** - Role-based access control not yet implemented.
3. **Single-tenant by default** - Multi-tenancy features available but not enabled by default.

## Security Checklist for Contributors

Before submitting code:

- [ ] No hardcoded secrets or credentials
- [ ] All user inputs validated and sanitized
- [ ] SQL queries use parameterized statements where applicable
- [ ] Error messages don't expose sensitive information
- [ ] New endpoints include appropriate rate limiting
- [ ] Security-relevant changes documented
- [ ] No new dependencies with known vulnerabilities

## Vulnerability Disclosure Policy

We follow a coordinated disclosure process:

1. **Reporter** submits vulnerability privately
2. **We** acknowledge and assess within 72 hours
3. **We** develop and test fix
4. **We** release fix and security advisory
5. **Reporter** may publish details 30 days after fix (or sooner with agreement)

We credit reporters in our security advisories unless anonymity is requested.
